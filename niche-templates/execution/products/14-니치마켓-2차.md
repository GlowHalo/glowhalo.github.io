## ⚠️ 공개 상태 검증 시도 — 이번 회차의 핵심 판단

이 세션의 Notion MCP는 tossneon@gmail.com 계정의 "나다컴퍼니" 워크스페이스에 연결돼 있다. 회장이 확인해준 대로 이 워크스페이스는 구 워크스페이스(`tossneon0`, `fearless-frog-802.notion.site`) 자료를 옮기는 **이관 목적지**이고, "상품 허브" 하위에 기존 20종 템플릿의 복제본이 이미 들어있다. 하지만 **이 새 워크스페이스 자체가 실제로 웹에 공개된 상태인지(자체 `*.notion.site` 서브도메인이 붙어있는지, 페이지별 "웹에 공개" 토글이 상속되는지)는 이번 회차에 다음 4가지 방법으로 검증을 시도했으나 전부 결론에 도달하지 못했다:**

1. **`notion-fetch` 메타데이터 확인** — 페이지를 가져와도 공유/공개 상태를 나타내는 필드가 전혀 없다(`include_discussions`도 무관). Notion MCP 표준 fetch 도구 자체가 공개 여부를 노출하지 않는다는 걸 확인.
2. **웹 검색으로 인덱싱 여부 확인** — "상품 허브" 페이지의 고유한 한국어 설명 문구, "Investor Panel — 3 AI VCs..." 제목으로 각각 검색했으나 이 워크스페이스가 인덱싱된 흔적을 찾지 못했다(검색엔진 미인덱싱은 최근 생성 때문일 수도 있어 결정적 증거는 아님).
3. **Cloudflare Browser Rendering으로 직접 스크린샷** — `www.notion.so/<페이지ID>`(로그인 없는 익명 요청, User-Agent 스푸핑까지 시도)로 렌더링해봤으나, 로그인 여부·공개 여부와 무관하게 "Your browser is not compatible with Notion" 안내만 뜬다 — 이건 Notion이 헤드리스 브라우저 자체를 감지해서 보여주는 공통 화면으로 보이며, 공개/비공개를 구분하는 신호가 아니다.
4. **Notion 공식 REST API의 `public_url` 필드 직접 조회** — 금고의 `notion_token`(pixel-ai-office용 별도 통합)으로 `GET /v1/pages/:id`를 호출하면 페이지가 공개 상태일 때 실제 `*.notion.site` URL이 담긴 `public_url` 필드가 내려온다(가장 신뢰할 수 있는 방법이었음). 하지만 이 통합은 이 페이지들과 공유돼 있지 않아 `object_not_found` — Notion의 "커넥션 연결"은 UI에서 페이지별로 직접 승인해야 하는 절차라 API만으로는 우회할 수 없었다.

**결론: 확실한 공개 확인 방법을 찾지 못했다.** 지시받은 원칙대로, 콘텐츠(Notion 빌드) 자체는 5종 전부 완성했지만 **Gumroad 발행은 진행하지 않았다.** 무작정 발행부터 하면 구매자가 비공개 페이지 링크를 받고 못 여는 사고가 날 수 있어서다.

### 다음 세션이 이어받을 것 — 공개 여부 확인 후 발행

이 워크스페이스가 실제로 공개 도메인을 갖고 있는지는 다음 중 하나로 확인 가능할 것으로 보인다(이번엔 시도만 하고 완결하지 못함):
- **가장 확실한 방법**: 회장이 Notion 설정(Settings & members → Sites 또는 워크스페이스 도메인 설정)에서 "상품 허브" 페이지가 실제로 웹에 공개돼 있는지, 공개돼 있다면 어떤 `*.notion.site` 서브도메인인지 직접 확인해 채팅으로 알려주면 즉시 해결된다. **API/자동화로 못 찾은 유일한 이유는 이 정보 자체가 API에 노출 안 되기 때문**이지 권한 문제가 아니다.
- **대안**: `notion_token` 통합을 "상품 허브" 페이지(또는 그 상위)에 회장이 직접 연결(Connections)해주면, 이후 세션이 `public_url` 필드로 API 확인·자동화까지 전부 셀프로 처리 가능.
- 둘 중 하나로 공개가 확인되면, 이 문서의 5종 콘텐츠는 이미 100% 완성돼 있으므로 [13번 문서](13-니치마켓-확장.md)와 동일한 절차(커버 3장 제작 → Gumroad `POST /v2/products` → 커버 임포트 → WELCOME2 할인코드 → `PUT`으로 custom_receipt 별도 설정 → `enable` → API+curl+픽셀 검증)로 바로 발행 가능.

## 실행 상세

1. **콘텐츠 제작**: 5개 상품 전부 직접 순차 생성(백그라운드 에이전트 병렬화 대신, Notion API 호출 자체를 직접 관리해 공개 검증 이슈에 바로 대응할 수 있게 함).
2. **Notion 빌드**: 루트 페이지 5개(상품 허브 하위) → 각 루트 하위에 Start Here + Prompt Sets(2개 페이지, 한 번의 `create-pages` 호출로 동시 생성) → DB(`create-database`, SQL DDL — `TEXT`가 아니라 `RICH_TEXT` 타입 키워드를 써야 한다는 걸 이번에 확인, `TEXT`로 시도하면 `validation_error`) → 데모 1행(`create-pages`, parent를 `data_source_id`로 지정).
3. **버그 발견·수정 1건**: 루트 페이지 생성 시 `title` 프로퍼티 텍스트에 이모지를 직접 넣고 `icon` 필드도 별도로 설정했더니, 실제 페이지에는 아이콘+타이틀이 둘 다 렌더링돼 "📦 📦 Amazon Listing Board"처럼 이모지가 중복 표시됐다. 기존 22개 상품은 title 프로퍼티에 이모지 없이 순수 텍스트만 넣고 아이콘은 `icon` 필드로만 설정하는 패턴이었음을 재확인 → 5개 전부 `update_properties`로 title에서 이모지 제거해 정정 완료.
4. **허브 페이지 갱신**: "🏪 상품 허브" 페이지 하단에 5종 링크 섹션 추가(`insert_content`), 공개 상태 미확인이라는 점도 섹션 제목에 명시.

## Gumroad 발행 — 보류 (2026-08-16)

**진행하지 않음.** 위 "공개 상태 검증 시도" 섹션 참고 — 4가지 방법으로 확인을 시도했으나 결론에 도달하지 못해, 지시받은 원칙("확실치 않으면 콘텐츠까지만 완료하고 발행은 보류")에 따라 멈췄다. 표준 스펙($11/$18, WELCOME2, 태그 8개, 커버 3장 브랜드 톤 등)은 13번 문서와 동일하게 그대로 적용할 준비가 돼 있고, 공개만 확인되면 바로 실행 가능한 상태다.
