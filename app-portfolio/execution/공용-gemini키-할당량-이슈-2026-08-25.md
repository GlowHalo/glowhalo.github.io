# 공용 Gemini 무료 키 할당량 소진 — 3개 앱 동시 장애 (2026-08-25)

## 무슨 일이 있었나

HQ 계정 정비 후속 점검 중 GlowHalo 6 소관 AI 앱 3종을 실호출로 확인하다가 발견했다.

- `glowhalo6-mindmap` `/generate` → **45초 넘게 무응답**(curl 타임아웃, 응답 자체가 안 옴)
- `glowhalo6-kpc-coach-chat` `/chat` → **100초 넘게 무응답**
- `glowhalo6-coach-practice` `/chat` → 62초 뒤 `502 {"error":"The operation was aborted"}`

원인은 공용 키 하나의 **일일 할당량 소진**이었다. 로그를 못 봐서 처음엔 원인이 안 보였는데,
아래 개선을 넣고 재호출하니 업스트림 원문이 그대로 드러났다:
`Gemini API error 429: "You exceeded your current quota, please check your plan and billing details."`

금고 `gemini_api_key`는 **무료 티어 키 하나**이고(모델당 하루 한도), 이 키를 위 세 Worker가
**같이** 쓴다. 즉 한 앱에서 한도를 태우면 나머지 두 앱도 같이 죽는다 — 앱별 장애가 아니라
그룹 공용 자원의 고갈이었다.

## 왜 증상이 앱마다 달랐나

`coach-practice`만 2026-08-19 코드리뷰 후속으로 타임아웃·재시도가 붙어 있었고, 나머지 둘은
없었다. 타임아웃이 없으면 업스트림이 응답을 안 줄 때 Worker가 그냥 매달린다 — 사용자에게는
"영원히 로딩 중"으로 보인다. **"느리지만 언젠가 오겠지"와 "지금 안 된다"는 완전히 다른 경험**이라,
같은 근본 원인이어도 체감 품질 차이가 컸다.

## 조치 (2026-08-25)

1. **`shared/worker-utils/gemini-fetch.ts` 신설** — 타임아웃(15초)·재시도(1회)·할당량 소진 감지를
   한 곳에 모았다. 세 Worker가 전부 이걸 쓴다. 상대경로 import만 하면 wrangler(esbuild)가 번들에
   넣어주는 것을 실배포로 확인했으므로 **다른 계열사 Worker도 그대로 재사용 가능**하다.
2. **할당량 소진(429 + quota/RESOURCE_EXHAUSTED)은 재시도하지 않는다** — 하루 한도는 몇 초 기다린다고
   풀리지 않는다. 대신 사용자에게 원문 JSON 대신 이렇게 안내한다:
   "공용 무료 AI 키의 하루 사용량을 다 썼습니다(그룹의 여러 앱이 이 키를 함께 씁니다).
   내일 다시 시도하시거나, 설정에서 본인 Gemini API 키를 등록하면 한도 없이 바로 쓰실 수 있습니다."
   → 사용자를 BYOK(본인 키 등록)로 자연스럽게 유도하는 문구이기도 하다.
3. **mindmap의 이중 재시도 제거** — 핸들러가 `callGemini`를 통째로 한 번 더 부르고 있어서, 재시도가
   곱해져(2×3×20초) 최악 2분 넘게 매달렸다. 재시도는 공용 유틸 한 곳에서만 한다.
4. **`coach-practice` 서버측 일일 상한 하향(150/30 → 40/8)** — 원래 숫자는 이 앱 하나만 보고 정한
   값이라, 공용 무료 키를 세 앱이 나눠 쓴다는 현실과 안 맞았다(한 사람이 그날 그룹 전체 몫을
   태울 수 있었음).

## 남은 판단 (회장)

무료 티어 키 하나를 세 앱이 공유하는 구조 자체는 그대로다 — 지금은 실사용자가 거의 없어서
"체험용으로 충분"하지만, 앱이 실제로 알려지기 시작하면 **매일 이 장애가 반복된다.** 선택지:

- **(A) 지금처럼 둔다** — 비용 0. 체험 한도를 넘긴 사용자는 BYOK로 유도(이미 세 앱 다 구현됨).
  실사용자가 적은 지금은 이게 합리적. 다만 "오늘 체험 못 해본 사람"이 매일 생긴다.
- **(B) 유료 키로 전환** — 체험 품질이 안정되지만 우리 비용이 발생한다. 2026-08-18 확정된
  수익화 원칙("우리 비용이 드는 기능을 무제한 무료로 방치하지 않는다")과 어긋나지 않으려면
  체험 한도는 그대로 두고 "한도 안에서는 확실히 동작"만 사는 셈.
- **(C) 앱별로 키를 분리** — 한 앱의 소진이 다른 앱을 죽이지는 않게 된다. 무료 키를 앱마다 따로
  발급하면 비용 0으로도 가능하지만, **계정당 한도**일 수 있어 실효가 없을 수 있다(확인 필요).

지금 판단은 **(A) 유지 + 앱이 실제로 트래픽을 받기 시작하면 재검토**를 권한다 — 지금 (B)로 돈을
쓰는 건 아직 검증 안 된 수요에 선투자하는 셈이라 무자본 검증 우선 원칙과 어긋난다.
