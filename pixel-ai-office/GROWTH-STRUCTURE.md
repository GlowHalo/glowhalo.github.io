# 새사업 스튜디오 확장 구조 제안 — 스튜디오 → 사업부서 → 관계사

이 문서는 "사업기회 발굴" 서사 재작성(HANDOFF.md 미완료 작업 2) 완료 후, 회장님 요청으로
"사업팀을 계속 늘려갈 수 있는 구조"를 다방면으로 분석해 제안한 것이다. 지금 당장 코드를
바꾸는 문서가 아니라 **의사결정용 로드맵**이다. 실행할 항목이 정해지면 그때 별도 작업으로
쪼갠다.

## 0. 지금 상태 요약

`pixel-ai-office`(= "새사업 스튜디오")는 회장님이 직접 CEO로 뛰는, `biz-exploration/`(정연이 이끄는
AI 사장 체제)와는 완전히 별개인 **단일 사업 탐색 오피스**다. 하루 사이클 동안 12개 부서가
협업해 사업기회 후보를 스캔 → 발산 → 검증 → TOP1 승인 → 실행 실험(랜딩/인터뷰)까지 돌리고,
그 결과를 매일 반복한다.

지금 구조가 답하지 못하는 질문: **"검증된 사업이 여러 개 쌓이면, 그다음은 어떻게 조직화하나?"**
이 문서는 그 답을 세 가지 모델로 나눠 분석하고, 하나를 고르라고 강요하지 않고 **시간순으로
엮어서** 제안한다 — 셋은 경쟁 관계가 아니라 성장 단계다.

## 1. 지금 구조의 구조적 한계 (진단)

| 한계 | 원인 | 영향 |
|---|---|---|
| 부서를 12개 이상 늘릴 수 없음 | `world.ts`의 오피스 레이아웃이 4×3=12칸으로 하드코딩 | 신사업이 늘어나도 화면에 자리가 없음 |
| 하루에 TOP1 아이디어 1개만 승인 | `dayScript()`가 승인 지점을 1곳만 두는 선형 시나리오 | 여러 후보를 동시에 검증 못 함 |
| "정착" 판정 기준이 없음 | 검증 실험 결과를 자동으로 누적·채점하는 로직 없음 | 성공해도 다음 조직 단계로 넘어갈 트리거가 없음 |
| 회사 이름이 하나("새사업 스튜디오")로 고정 | `company.config.ts`가 계열사 개념 없이 설계됨 | 사업이 자라도 브랜드가 분리 안 됨 |

이 넷은 전부 **"아직 하나도 안 만들어서 생긴" 한계**지, 설계가 잘못된 게 아니다. 오히려
`company.config.ts` 하나만 고치면 되는 지금 구조(모노레포 + "한 파일만 고치면" 원칙)는
아래 3번 모델(관계사)의 토대로 그대로 재사용된다.

## 2. 세 가지 확장 모델

### A. 스튜디오 체계 — 여러 아이디어를 병렬로 실험

**설명**: 지금처럼 하나의 허브 조직(새사업 스튜디오)이 자원(12개 팀·32명)을 공유하면서
동시에 여러 개의 소규모 검증 실험을 굴린다. 실리콘밸리 벤처 스튜디오(예: Atomic, Expa)나
Rocket Internet식 "동시다발 가설 테스트" 모델과 같은 형태.

**장점**
- 자원 재사용 — 리서치·리스크점검·비서 같은 공통 기능팀을 아이디어마다 새로 안 만들어도 됨
- 학습 전이 — 오늘의 실패("이미 레드오션") 경험이 내일 다른 아이디어 검증에 바로 반영됨
- 실패 비용이 낮음 — 하루 사이클이라 하나가 죽어도 다음날 바로 새 후보로 교체

**단점**
- 집중력 분산 — 후보가 3~4개로 늘면 각 실험에 배정되는 인원·시간이 줄어 판정이 늦어짐
- 브랜드 정체성이 약함 — "새사업 스튜디오"라는 이름 아래 이질적인 사업 여러 개가 섞임
- 12칸 고정 레이아웃이라 "복수 병렬 검증"을 화면에 표현하려면 UI 재설계가 필요

**지금 코드에 적용한다면**: `dayScript()`의 TOP1 승인 지점을 TOP3 전부 병렬 검증(랜딩A/B를
아이디어별로)으로 확장하는 정도가 현실적 1단계. 부서 슬롯 자체를 늘리는 건 하지 않는다 —
대신 "이번 주 3번째 검증 사이클"처럼 **같은 12개 부서로 아이디어를 순차/병렬로 여러 번
돌리는 게** 스튜디오 모델의 핵심이라, 지금 구조가 이미 이 모델의 1인 버전이다.

### B. 신사업팀 → 사업부서 축적 — 승격 사다리

**설명**: 검증된 아이디어에 단계별로 더 많은 자원과 자율성을 부여하는 4단계 사다리.

| 단계 | 이름 | 자원 | 승격 게이트(예시 기준) |
|---|---|---|---|
| 0 | 실험 (Experiment) | 하루 사이클, 겸직 32명 | — (지금 구조) |
| 1 | 신사업팀 (Pilot) | 전담 1~3명, 4~8주 | 랜딩 신청 전환율 N% 이상 **또는** 인터뷰 8명 중 M명 이상 긍정 |
| 2 | 사업부서 (Business Unit) | 전담 팀 + 자체 예산선 | 4~8주 파일럿 동안 반복 매출/재사용 지표 D회 이상 달성 |
| 3 | 계열사 (Affiliate) | 완전 분리된 조직·브랜드 | 사업부서 단계에서 회장님 개입 없이 자체 P&L 운영 M개월 이상 |

**핵심은 "감정적 판단 배제"**: 지금 시뮬레이션의 QA/리스크 점검팀이 이미 "근거 없으면
반려"라는 원칙을 갖고 있는 것처럼, 승격도 숫자 기준이 없으면 유야무야된다. 위 표의 기준값은
초안이라 실제 사업 성격에 맞게 회장님이 확정해야 한다.

**단계 2에서 눈여겨볼 precedent**: `biz-exploration/`의 "AI 사장 정연" 구조가 이미 이 단계 2~3의
실제 사례다. 사업부서가 사람 개입 없이도 돌아갈 만큼 자리잡으면, 그 사업에 전담 AI
의사결정자를 앉히는 패턴은 이미 이 저장소 안에 검증돼 있다 — 새로 발명할 필요 없이 그
구조를 재사용하면 된다.

### C. 관계사 구조 — 오피스 복제본 운영

**설명**: 사업부서가 정착하면, `pixel-ai-office` 자체를 복제해 그 사업 전용 오피스를
독립적으로 띄운다.

**이 저장소 구조와 정확히 맞아떨어지는 이유**: 루트 CLAUDE.md 원칙 — "새 프로젝트 = 루트에
영문 slug 폴더를 추가", "독립 주소가 꼭 필요해지면 `git subtree split`으로 분리" — 가 이미
관계사 복제 메커니즘 그 자체다. 절차는 이렇다.

1. `pixel-ai-office/` 전체를 새 슬러그 폴더(예: `subscription-biz/`)로 복사
2. `company.config.ts` 하나만 그 사업에 맞게 다시 채움 (회사명·부서 12개·직원 명단 —
   지금 "여기 한 파일만 고치면 됩니다" 설계가 그대로 재사용됨)
3. `sim.ts`의 서사는 그 사업 단계에 맞게 다시 씀 (예: 신사업 탐색이 아니라 "운영 최적화"나
   "고객 성장" 흐름으로) — 이번에 한 재작업이 바로 이 절차의 리허설이었던 셈
4. 루트에서 push 한 번 → `tossneon.github.io/subscription-biz/`로 독립 배포
5. 계열사가 3개 이상 쌓이면 루트에 "계열사 지도" 허브 페이지(각 오피스 링크 + 상태 요약)를
   하나 만들어 관리

**장점**: 새 코드를 안 만들어도 됨 — 이미 있는 패턴 재사용. 각 계열사가 시각적으로도
완전히 분리되어 브랜드 혼재 문제(A의 단점)가 해결됨.

**단점**: 오피스 하나 만들 때마다 `company.config.ts`를 손으로 채워야 함(자동화 없음).
계열사가 늘어날수록 "루트 하나에 프로젝트 폴더가 계속 늘어나는" 모노레포 자체의 탐색
난이도가 올라감 — registry.js/Notion 허브가 있어서 지금은 괜찮지만, 10개 넘어가면
허브 페이지가 필수가 된다.

## 3. 세 모델 비교

| | A. 스튜디오 | B. 사업부서 축적 | C. 관계사 복제 |
|---|---|---|---|
| 지금 코드로 가능? | 부분적으로 (TOP3 병렬 검증 확장 정도) | 아니오 — 게이트 로직 신규 필요 | 예 — 기존 모노레포 원칙 그대로 |
| 필요한 신규 개발 | 중간 (dayScript 병렬화) | 낮음~중간 (수치 기준 + 로그만) | 낮음 (반복 작업, 새 로직 거의 없음) |
| 자원 효율 | 높음 (공유) | 중간 (전담 인원 필요) | 낮음 (완전 분리) |
| 브랜드 명확성 | 낮음 | 중간 | 높음 |
| 언제 쓰나 | 검증 단계(하루~몇 주) | 파일럿~초기 운영(몇 주~몇 달) | 정착 이후(몇 달 이상) |

## 4. 권장 로드맵 — 세 모델은 시간순으로 이어진다

경쟁하는 선택지가 아니라 **한 사업의 생애주기**로 보는 게 맞다.

```
[A] 스튜디오에서 매일 후보 검증
        │  (같은 아이디어가 N회 연속 TOP1 승인 + 리스크점검 통과)
        ▼
[B-1] 신사업팀 파일럿 (전담 1~3명, 4~8주)
        │  (전환율/재구매 등 수치 게이트 통과)
        ▼
[B-2] 사업부서 (자체 예산선, 이 시점부터 "다음 계열사 후보"로 공식 표기)
        │  (회장님 개입 없이 자체 운영 M개월 이상)
        ▼
[C] 관계사 — 오피스 복제, 독립 주소, (선택) AI 사장 배치
```

**지금 당장 할 필요는 없는 것**: 12칸 레이아웃 확장, 계열사 허브 페이지, 승격 자동화 —
전부 "지금 검증 중인 사업이 실제로 하나라도 B-1까지 가면" 그때 만들어도 늦지 않는다.
사업기회 자체가 아직 하나도 확정 안 된 지금 단계에서 조직 확장 코드부터 만드는 건
"제품 없이 회사 로고부터 만드는" 순서 역전이다.

**지금 할 만한 가벼운 1단계 (원하시면 별도 작업으로 진행)**:
- `review`(검증 회고팀)의 하루 로그에 "이번이 몇 번째 검증 사이클인지", "지난 사이클과
  같은 아이디어인지"를 누적 기록하는 정도의 가벼운 카운터. B의 승격 게이트를 나중에
  판단할 때 쓸 최소한의 데이터만 지금부터 쌓아두는 것.

## 5. 결론

세 모델 다 필요하지만 순서가 있다. 지금은 A(스튜디오)로 충분하고, **아이디어가 실제로
하나라도 살아남기 전까지는 B·C를 위한 코드를 미리 만들 필요가 없다.** 이 문서는 그때가
왔을 때 바로 참고할 수 있도록 미리 정리해둔 것이다.
