# 네이버 스마트스토어 × 버크만 자동화 — 프로세스 설계 (2026-08-16)

회장이 제시한 10단계 자동화 프로세스를 점검하고 빈 곳을 보완한 기록. 실제 구현 착수 전 설계 단계 — 코드는 아직 없음.

## 원안 (회장 제시, 2026-08-16)

1. 네이버에 주문 발생(판매자API)
2. 주문 정보 추출하여 버크만코리아 사이트에서 진단지 구매(당분간 결제 직전까지만 자동화)
3. 구매한 진단지에 주문 정보 적용하여 진단지 발송
4. 네이버에 발송처리 완료 체크(디지털 배송 15일 후 구매확정 체크 필요)
5. 특정 시점까지 미수행 시 리마인드
6. 진단 완료 모니터링
7. 진단결과지 확보 및 디브리핑 자료 제작(결과지 정상 발송 여부 체크)
8. 디브리핑 자료 첨부 메일 발송
9. 관리대장 기입(내부관리용)
10. 월별 비용/수익 관리

## 확정된 전제 (2026-08-16)

- **네이버 API = 커머스API.** 앱 등록: https://apicenter.commerce.naver.com/ko/basic/main (스마트스토어 판매자 계정 로그인 필요, 스토어당 앱 1개 한도). **스마트스토어 판매자 계정은 회장이 준비 중** — 완료 전까지 이 라인은 설계만 진행.
- **버크만이 초대메일 + 결과리포트 메일을 둘 다 자동발송**(회장 전언 — 결과리포트 쪽은 "일걸"로 미확정, 재정찰 때 최종 검증). 맞다면 우리가 실제로 발송하는 메일은 **디브리핑 하나뿐**.
- **도메인: `nadagroup.org`**(2026-08-16 구매, Cloudflare Registrar) — Reflect Lab 전용이 아니라 GlowHalo Group 공용 zone, HQ 통합관리. Resend 발신 도메인 인증은 이 zone의 서브도메인으로 진행(예: `mail.reflectlab.nadagroup.org`). **막힘**: 현재 금고의 `cloudflare_api_token`이 이 zone에 대한 DNS 편집 권한이 없음(`zones/dns_records` 호출 시 Authentication error) — Zone:DNS:Edit 권한을 포함한 토큰 재발급 또는 기존 토큰에 zone 추가 필요.

## 재정의된 단계별 책임

발송 주체가 갈리면서 원안의 3·7·8번 의미가 바뀐다.

| # | 단계 | 발송/확인 주체 | 비고 |
|---|---|---|---|
| 1 | 네이버 주문 감지 | 우리(폴링) | 커머스API는 웹훅이 아니라 폴링 방식 — 주기적 조회 필요 |
| 2 | 버크만 대상자 등록 + 진단지 구매(결제 직전까지) | 우리 | `birkman.md` 확인게이트 그대로 유지 |
| 2-1 | 진단 초대메일 | **버크만 자동발송** | 대상자 등록 시 자동 트리거, 우리가 손댈 것 없음 |
| 3 | 네이버 발송처리 API 호출(즉시발송처리, 디지털상품) | 우리 | 구매 완료 직후 호출 — 안 하면 정산 지연 |
| 4 | 15일 자동구매확정 추적 | 우리(폴링/타이머) | 매출 확정 시점(재무 반영 시점)의 근거 |
| 5 | 미수행 리마인드 | 우리(Resend) | 최대 횟수 제한 필요(아래 예외처리 참고) |
| 6 | 진단완료 모니터링 | 우리(마이페이지 폴링) | "진단진행상태" 컬럼으로 확인 가능(2026-08-10 재정찰 확인됨) |
| 7 | 결과 PDF 확보(디브리핑 원본용) | 우리 | "결과지가 고객에게 정상 발송됐는지"는 우리가 검증 불가(버크만이 보내는 메일이라) → **체크 범위를 "우리가 마이페이지에서 PDF를 정상 다운로드했는가"로 재정의** |
| 7-1 | 결과리포트 메일 | **버크만 자동발송(추정)** | 재정찰로 최종 확인 필요 |
| 8 | 디브리핑 메일 발송 | 우리(Resend) | 유일하게 우리가 컨트롤하는 발송 |
| 9 | 관리대장 기록 | 우리 | 아래 PII 저장/파기 참고 |
| 10 | 월별 정산 | 우리 | `재무.md` 확장 |

## 빈 곳 보완

### 예외 처리

| 지점 | 상황 | 대응 |
|---|---|---|
| 네이버 주문 | 주문취소/반품 | 버크만 구매 전이면 스킵. 이미 구매했으면 환불 불가(진단지는 이미 결제됨) → 즉시 회장 에스컬레이션 |
| 버크만 구매 | 품절/사이트 오류/결제 실패 | 관리대장에 `구매실패` 기록 + 회장 알림. 자동 재시도는 최대 1회(중복결제 방지) |
| 대상자 등록 | 이메일 오탈자로 초대메일 반송 | 버크만 마이페이지의 반송 표시 여부는 재정찰 때 확인. 없으면 "N일 내 미개봉"을 반송 신호로 간주 |
| 리마인드 | 기한까지 미응시 | 최대 리마인드 횟수(제안: 2회) 이후 중단, `장기미응시` 표기 → N일(제안: 30일) 후 회장께 일괄 보고 |
| 결과 확보 | 완료됐는데 PDF 다운로드 실패 | 재시도 + N회 실패 시 사람 개입 알림. URL 패턴은 이미 알고 있어(`/mypage/download/assessment/each?num={data-member}`) 재시도 자체는 어렵지 않음 |
| 디브리핑 발송 | Resend API 오류/반송 | 기존 dry-run 원칙 유지, 자동 재시도 1회 후 실패 지속 시 알림 |
| 구매확정 | 15일 자동확정 전 위 문제 미해결 | 관리대장에 `확정전 이슈` 플래그 — 매출 인식(재무 반영)을 확정 시점 이후로 지연 |

### 동시 주문 처리

초기 물량은 순차 처리(큐 1개)로 충분 — 버크만 로그인 세션이 계정당 1개뿐이라 동시 다중 세션이 어차피 불가능. 물량이 늘면 대상자 대량업로드 엑셀 양식(`templates/대상자-대량업로드-양식.xlsx`)을 활용한 배치 처리로 전환 검토.

### 상시 실행 아키텍처 (제안)

Claude Code 세션은 상시 대기형이 아니므로 **Cloudflare Worker + Cron Trigger + D1**을 제안:
- Cron이 주기적으로(예: 1시간) 네이버 주문 폴링 + 버크만 진단상태 폴링 + 리마인드/구매확정 타이머 체크
- 브라우저 자동화가 필요한 단계(버크만 로그인=Browserbase, PDF 다운로드)는 Worker가 못 하므로, Worker가 "처리 필요" 큐에 쌓아두면 Claude 세션이 주기적으로 그 큐를 처리하는 하이브리드 구조

### PDF 다운로드 자동화 (기존 막힘 지점 해법 제안)

다운로드가 네이티브 저장 다이얼로그를 띄워 자동화가 막혔던 지점(2026-08-10 기록) — URL 패턴(`/mypage/download/assessment/each?num={data-member}`)은 이미 알고 있으므로, **로그인 성공 후 세션 쿠키를 추출해 그 쿠키로 직접 HTTPS GET**하면 UI 클릭·다이얼로그를 거치지 않고 파일을 받을 수 있을 가능성이 높음 — 다음 재정찰 때 같이 검증.

### PII 저장/파기 (제안 — 회장 확정 필요)

관리대장은 `data/orders.json`(gitignore 대상)에 저장, 필드: 주문번호/구매자명/이메일/전화/버크만등록여부/구매확정여부/진단상태/결과확보여부/디브리핑발송여부/타임스탬프. **파기 시점 제안**: 구매확정 + 디브리핑 발송 완료 후 90일 뒤 자동 삭제(세무/CS 대응 여유 고려) — 숫자는 제안일 뿐, `birkman.md` 정비 시 회장 확정 필요.
