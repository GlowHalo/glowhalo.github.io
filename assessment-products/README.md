# 나다컴퍼니4 — 관계사 헌장 (진단 상품화)

나다그룹 산하 네 번째 관계사. 대표: **채원** (2026-08-09 선임). 나다컴퍼니1/2(신사업 탐색)·나다컴퍼니3(자산운용)와 달리, **진단(심리/성향 검사) 상품화**를 전담한다 — 회장의 버크만 시그니처 디브리퍼 자격을 근간으로 시작해, 이후 자격 불필요한 진단군으로 라인업을 넓힌다.

공유 원칙(회장 리소스 제약, 공개저장소 주의, 조직 확장은 사후 기록·사전 승인 불필요, 신규 역할은 실명 없이 역할명만)은 루트 [`CLAUDE.md`](../CLAUDE.md)와 [`niche-templates/README.md`](../niche-templates/README.md)를 그대로 따른다. 이 문서는 나다컴퍼니4만의 차이점만 적는다.

## ⚠️ 확인 게이트 — birkman.md (가장 중요한 제약)

다른 계열사와 달리 실제 고객·실제 결제·실제 개인정보(진단 대상자 이름·이메일)가 오간다. 전체 규칙은 [`.claude/rules/birkman.md`](../.claude/rules/birkman.md)가 정본이며, 요약하면:

- **진단 구매는 실제 결제다** — 구매 자동화는 항상 확인 게이트 + dry-run, 결제 직전 재확인.
- **메일 발송도 실제 발송이다** — 기본 dry-run, `--send` 플래그로만 실제 발송.
- **버크만 사이트 로그인은 회장만** — 채원이 대신 로그인하지 않는다.
- 고객 개인정보·결과 PDF·세션 파일은 `data/`(gitignore) 밖으로 절대 안 나간다.
- 나다컴퍼니3의 실거래 게이트와 같은 이유(CLAUDE.md 자율성 원칙 1번 "되돌릴 수 없는 결정")로 다른 계열사보다 보수적으로 시작하고, 반복 운영으로 안정성이 확인되면 완화를 검토한다.
  - **⚠ 나다컴퍼니3 게이트는 2026-08-10에 해제됐지만(계좌·권한 범위 확정 완료), 이 계열사의 결제·발송 게이트는 그대로 유지된다.** 저쪽이 풀렸다고 이쪽이 자동으로 풀리는 게 아니다 — 근거가 "같은 원칙에서 출발했다"일 뿐, 해제 조건(회장의 명시적 권한 범위 확정)은 계열사마다 따로 충족돼야 한다. 이쪽 완화는 회장이 별도로 확정할 때 이 줄을 갱신한다.
- **2026-08-10 확정 — PII 처리 원칙 보강 논의 중**: 수집→처리→발송→**파기**까지 라이프사이클을 명시하고, 발송 전 이중 확인(스크립트 자체 검증 + 회장 최종 승인)을 구조화하는 방향으로 `birkman.md` 정비를 논의 중. 파기 주기·자동화 완화 기준(무사고 N건)의 구체 숫자는 회장 확정 대기.

## 초기 자율성 — 다른 계열사보다 낮게 시작

최종 목표는 완전 자동화(회장 개입 0)이지만, **브랜딩·스토어 개설·플랫폼 확장·상품 컨셉·상세페이지 등 초기 세팅은 회장과 긴밀히 협의하며 진행**한다 — 회장이 명시적으로 "많은 의견을 나누며 함께할 생각"이라고 밝혔기 때문. 정연/하윤/은성 체제(임원 독립검토 → 대표 종합 → 상신)와 달리, 채원은 각 결정을 회장과 옵션 제시 → 의견 수렴 방식으로 좁혀간다. 조사(무자격 진단 후보 리서치 등 실행에 해당하지 않는 영역)는 채원이 자율 진행.

## 브랜드 — Reflect Lab (2026-08-10 확정)

- 여러 라운드 논의 끝에 **"Reflect Lab"(리플렉트랩)** 로 확정. 후보였던 "The Reflect Room", "Reflectica"는 각각 톤 차이·상표 충돌 우려(Reflectica는 동일 카테고리의 해외 서비스 "Reflectica AI"와 이름 겹침)로 제외.
- 상표: 웹서치 기반 정황 확인만 완료(국내 동일업종 충돌 미발견). **KIPRIS 정식 검색은 세션 도구 한계로 자동 수행 불가** — 정식 상표 출원은 실제 매출 발생 후 재검토(그 전엔 브랜드명으로만 사용, 사업자등록·정식출원 모두 불필요 — 개인 명의 출원도 가능).
- "구매대행이 티나면 안 됨"이 브랜딩 요건 — 상세페이지·고객 접점 어디에도 버크만코리아 대행 관계를 노출하지 않는다.

## 네이버 스마트스토어 판매 자동화 (2026-08-16 착수)

버크만 구매대행 파이프라인을 실제 판매 채널(네이버 스마트스토어, 커머스API)과 엮는 자동화 설계에 착수. 10단계 프로세스 점검·예외처리·아키텍처 제안을 [`execution/네이버자동화-프로세스설계.md`](execution/네이버자동화-프로세스설계.md)에 정리해뒀다 — 다음 세션은 이 파일부터 볼 것.

- 도메인: **`nadagroup.org`**(2026-08-16 회장 구매, Cloudflare Registrar, HQ 공용 zone) — Reflect Lab 전용 도메인이 아니라 나다그룹 공용 도메인이다. Resend 발신 도메인 인증은 이 zone의 서브도메인(예: `mail.reflectlab.nadagroup.org`)으로 진행 예정 — 아직 DNS 레코드 등록 전(현재 `cloudflare_api_token`에 이 zone에 대한 DNS 편집 권한이 없어 막힘, 확인 필요).
- 버크만 사이트가 진단 초대 메일 + 결과 리포트 메일을 **둘 다 자동발송**하는 것으로 잠정 확인(회장 전언, "일걸"로 미확정) — 사이트 재정찰 때 최종 검증 필요. 이게 맞으면 우리가 실제로 보내는 메일은 **디브리핑 하나뿐**이라 Resend 도메인 인증 범위가 좁아진다.
- 네이버 API = **커머스API**로 확정. 앱 등록은 [커머스API센터](https://apicenter.commerce.naver.com/ko/basic/main)에서 스마트스토어 판매자 계정으로 로그인 후 진행.
- **스마트스토어 판매자 계정 — 회장 준비 중(2026-08-16).** 이게 끝나야 커머스API 앱 등록(클라이언트ID/시크릿 발급)이 가능 — 그 전까지 이 라인은 설계만 계속 진행.
