# 계열사 세션 승인 팝업 완화 — 대기 중 (2026-08-19)

**상태: 보류 — 저장소 이전(GlowHalo 개명·마이그레이션) 끝난 뒤 착수.**

## 회장 지시 원문

> "세션들이
> 1. 데이터반영을 지시해서 노션에 접근할때
> 2. 정기보고 등을 지시해서 루틴을만들때
> 계속 승인팝업을 띄우네.
> 안띄우도록 조치해줘.
>
> 지금은 저장소 정비중이니 기억했다가 완료되고나면 이어서해줘"

즉 계열사 세션들이 아래 두 카테고리 도구 호출 시 여전히 대화형 승인 팝업이 뜬다:
1. **Notion 데이터 반영** — `mcp__Notion__*` 쓰기 계열 호출(예: notion-update-page 등)
2. **루틴/트리거 생성** — `mcp__Claude_Code_Remote__*`의 create_trigger/update_trigger 등

## 지금까지 확인한 것 (2026-08-19 새벽, `.claude/settings.json` 진단)

`permissions.allow`에 이미 와일드카드 존재:
- `"mcp__Claude_Code_Remote__*"`
- `"mcp__Notion__*"`

`autoMode.allow`에도 각각 상세 근거 문구가 이미 있음:
- Notion 쓰기 작업(trash 이동 포함) 승인 없이 진행하라는 문구 — 2026-08-?? 작성
- 루틴/트리거 도구는 **MCP 서버 해시프리픽스 무관하게 매칭**하라는 문구까지 이미 추가돼 있음("MATCH BY TOOL-NAME SUFFIX REGARDLESS OF MCP SERVER PREFIX", 2026-08-17 정연 세션 사례로 명확화)

→ **"권한 규칙이 아예 없어서" 뜨는 문제가 아니다.** 그런데도 팝업이 계속 뜬다는 게 회장 보고이므로, 근본 원인이 따로 있을 가능성이 높다. 재개 시 확인할 후보:

1. **Notion 쪽도 루틴/트리거처럼 해시프리픽스 무관 매칭 문구가 필요한가?** — `mcp__Notion__*`도 세션마다 `mcp__Notion__notion-update-page` vs `mcp__<해시>__notion-update-page`로 다르게 보일 가능성 확인 필요(루틴 도구에서 실제로 그랬던 전례가 있음).
2. **`permissions.allow`의 서버-이름 위치 와일드카드(`mcp__Notion__*`)가 기술적으로 유효한가?** — 이 세션에서 이전에 확인한 별개 사실: Edit 도구 자체는 서버 이름 자리에 와일드카드를 쓰는 패턴을 거부하고, 끝(도구 이름) 자리 와일드카드만 허용했었다. `permissions.allow`가 런타임에서 동일한 제약을 받는지, 아니면 별도 파서라 괜찮은지 미확인.
3. **`autoMode.allow`와 `permissions.allow`가 실제로 서로 다른 역할인가?** — 하나는 팝업 자체를 억제하고 다른 하나는 그냥 참고용 근거 로그일 수도 있음. 정확한 집행 메커니즘 미확인 — 필요하면 공식 문서(claude-code-guide 에이전트) 확인.
4. 계열사 세션이 **루트 `.claude/settings.json`을 실제로 읽고 있는지**(모노레포 cwd 문제) — `plugin-marketplace.md`에 기록된 별개 조사에서 "계열사 세션이 자기 폴더를 cwd로 시작하는지 저장소 루트로 시작하는지 미확인"이라는 유사 열린 질문이 있었음. 이것도 같은 계열의 문제일 수 있음 — 만약 계열사 세션이 하위폴더를 cwd로 시작한다면 그 폴더 안에 별도 `.claude/settings.json`이 있는지, 없다면 루트 설정을 정말 상속받는지 확인 필요.

## 재개 시 작업 순서(제안)

1. 위 4가지 후보 중 하나(특히 1·4번)부터 실제 계열사 세션 하나(예: 다연/GlowHalo 9 — 최근 활동)에서 직접 재현 확인.
2. 원인 확정되면 `.claude/settings.json` 수정(필요 시 Notion에도 해시프리픽스 무관 문구 추가, 또는 다른 근본 수정).
3. 수정 후 실제로 팝업이 없어졌는지 계열사 세션에서 검증(회장 확인 요청 또는 다음 정기 브리핑 때 자연스럽게 트리거되는 호출로 확인).

## 2026-08-19 — 새 HQ 세션 착수, 근본 원인 공식 확인 + 수정 시도는 플랫폼 안전장치에 막힘

**후보 2번(`permissions.allow` 서버-이름 자리 와일드카드가 유효한가)이 확정됐다 — 공식 문서 기준.** claude-code-guide 에이전트로 `code.claude.com` 공식 문서(`permissions.md`, `auto-mode-config.md`)를 직접 조회해 확인:

- `permissions.allow`의 MCP 규칙은 **서버 이름 세그먼트가 바이트 단위로 정확히 일치해야** 매칭된다. `mcp__Notion__*`처럼 친숙한 이름으로 적은 규칙은 `mcp__6683386a-a969-4401-83e3-ccfbe0ff3843__notion-update-page`처럼 해시 프리픽스로 뜨는 세션에서는 **절대 매칭되지 않는다.**
- **서버 이름 자리 와일드카드(`mcp__*__toolname`)는 `permissions.allow`에서 유효한 문법이 아니다** — 도구 이름 자리(끝)만 와일드카드 가능하고, 서버 이름 자리는 항상 리터럴이어야 한다. 즉 `permissions.allow`만으로는 "해시 프리픽스 무관하게 이 도구 허용"을 표현할 방법이 구조적으로 없다.
- `autoMode.allow`는 완전히 다른 메커니즘이다 — 리터럴 패턴이 아니라 **분류기(LLM)가 읽는 자연어 서술**이라서, "서버가 뭐든 이 도구는 승인" 같은 의도를 문장으로 적으면 분류기가 이해할 수 있다. 이게 유일하게 해시 프리픽스와 무관하게 동작할 수 있는 경로다.
- 이 세션 자체에서 실측 확인: 이번 세션에 연결된 Claude Code Remote·Notion·Gmail·Google Drive가 전부 해시 프리픽스로 뜨고(`mcp__bf7c680d-...`, `mcp__6683386a-...`, `mcp__8bba4249-...`, `mcp__eeefc882-...`), GitHub만 `mcp__github__*`로 친숙한 이름을 유지한다.

**단, 완전한 해결로 단정할 수 없는 이유**: `autoMode.allow`에는 이미 2026-08-17에 루틴/트리거 도구용 "MATCH BY TOOL-NAME SUFFIX REGARDLESS OF MCP SERVER PREFIX" 문구가 추가돼 있었는데도, **바로 오늘(2026-08-19) 같은 유형의 팝업이 정연·은성·예슬 세션에서 다시 재현됐다**(위 "글로우헤일로 전면개명" 문서 1차 점검 기록 참고). 즉 분류기 프롬프트에 규칙을 적어두는 것만으로 100% 신뢰할 수 있다는 보장은 없다 — LLM 분류기이기 때문에 매번 정확히 적용된다는 확실성이 리터럴 매칭보다 낮다.

**시도한 조치**: 위 확정 결론에 따라 Notion·Gmail·Google Drive에도 루틴/트리거와 동일한 "해시 프리픽스 무관 매칭" 문구를 `autoMode.allow`에 추가하려 했으나, **`.claude/settings.json` 자체를 수정하는 Edit 호출이 플랫폼 auto mode 분류기에 의해 차단됐다** ("Blocked by classifier" — 자기 권한을 스스로 확장하려는 시도로 판단된 것으로 보임). CLAUDE.md 원칙("의도된 안전장치는 우회 대상이 아니다")에 따라 다른 도구로 우회 시도하지 않고 회장 판단을 구하기로 함 — 회장이 직접 편집하거나, 명시적으로 승인하면 그때 반영한다. 초안은 이 세션 대화 기록에 있음(Notion/Gmail/Drive용 자연어 규칙 3건 + 기존 루틴/트리거 규칙에 "오늘 재현됨, 100% 신뢰 금지" 캐비엇 추가).

**다음 필요 조치**: 회장이 `.claude/settings.json`을 직접 열어 위 초안을 반영하거나, "이 편집 진행해도 된다"고 명시적으로 승인해줄 것. 반영되더라도 "완전히 해결됨"이라 단정하지 말고 며칠간 계열사 세션에서 재현 여부를 계속 관찰할 것.

## 2026-08-25 — 근본 원인 최종 확정: `Bash(*)` 등 광범위 allow 규칙은 auto 모드 진입 시 자동으로 무시된다 (설계상 의도, 우회 불가)

GlowHalo2(하윤) 세션이 `permissions.allow`에 `Bash(*)`가 이미 전면 허용돼 있음에도(2026-08-17 회장 승인) 평범한 `curl` 명령 하나에도 계속 승인 팝업이 뜨는 걸 실측 확인 → 이번엔 MCP 도구가 아니라 **순수 Bash 명령**이라 위 해시프리픽스 이론으로는 설명이 안 됨 → `claude-code-guide` 에이전트로 공식 문서(`code.claude.com/docs/en/permission-modes`, `permissions`) 재조사, 확정 답변 확보:

- **`permission_mode: "auto"`로 들어가는 순간, `Bash(*)`처럼 "임의 코드 실행"급으로 넓은 allow 규칙은 통째로 무시(dropped)된다** — 문서에 명시된 설계 동작이다. `Bash(npm test)`처럼 좁은 규칙은 계속 유효하지만, 우리 저장소처럼 `Bash(*)` 하나로 전부 열어둔 방식은 auto 모드에서 사실상 없는 셈 취급된다.
- 대신 그 자리를 **분류기(LLM)가 매 호출마다 개별 판단**하는 방식이 채운다 — 이게 바로 우리가 계속 목격해온 "허용 규칙이 있는데도 뜨는 팝업"의 정체다.
- 결정 순서(문서 원문 근거): deny 규칙 최우선 차단 → ask 규칙은 더 구체적인 allow가 있어도 무조건 프롬프트 → 좁은 allow만 분류기 검토를 건너뜀 → 넓은 allow(`Bash(*)` 등)는 드롭됨 → 나머지는 전부 분류기행.
- **게다가 이건 `permissions.allow`를 아무리 정교하게 고쳐도 못 피한다** — `.claude/`·`.git` 같은 보호 경로 쓰기, 위험 경로 `rm`, 특정 MCP 도구 등은 allow 매칭 여부와 무관하게 항상 분류기 재검토 또는 완전 차단 대상으로 문서에 명시돼 있다("permissions.allow rules in settings files do not pre-approve protected-path writes. The safety check runs before Claude Code evaluates allow rules").

**결론 — 이건 버그도, 설정 미비도 아니라 auto 모드의 설계 의도다.** CLAUDE.md 원칙("의도된 안전장치는 우회 대상이 아니다")에 따라 `.claude/settings.json`을 더 손보는 방향은 더 이상 유효한 해법이 아니다(애초에 그 시도조차 2026-08-19에 플랫폼 분류기에 막혔던 것도 같은 이유였을 가능성이 높음). **유일한 실질적 레버는 그 세션의 `permission_mode` 자체를 `auto`에서 `acceptEdits`나 `bypassPermissions` 같은 다른 모드로 바꾸는 것뿐**인데, 이는 "그 세션에서 뭘 물어보고 뭘 안 물어보는지"의 안전 경계 자체를 바꾸는 일이라 계열사별로 조용히 바꿀 게 아니라 회장이 각 계열사에 원하는 모드를 명시적으로 정해줘야 하는 사안이다. 상세 근거는 이 세션(HQ) 대화 기록(2026-08-25) 참고 — 공식 문서 URL: `code.claude.com/docs/en/permission-modes`, `code.claude.com/docs/en/permissions`.
