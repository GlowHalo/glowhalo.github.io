# 헤드리스 브라우저 자동화 인프라 — Browserbase 대안 검토

**상태**: ✅ 확정·구현·실전 검증 완료 (회장이 새 Cloudflare 토큰 발급 → 금고 등록 → 하윤이 RapidAPI 가입 자동화에 실제 적용해 폴백까지 확인)

**실전 검증 결과(2026-08-10)**: GlowHalo 2가 RapidAPI Hub 가입 자동화에 이 이중화 구성을 실제로 써봄 — 그 시점에 Cloudflare 쪽 하루 할당량이 이미 소진돼 있었는데(`429 Rate limit exceeded`), 코드의 자동 폴백이 정상 작동해 **Browserbase로 즉시 이어받아 가입 진행 성공**. 메인/백업 이중화가 설계대로 동작함을 확인. 상세: [`niche-api/products/link-preview-api/README.md`](../../niche-api/products/link-preview-api/README.md#rapidapi-등록-진행-상황-2026-08-0910).

**✅ 2026-08-11 — 무료 한도 소진 문제 자체를 회장이 근본 해결.** 같은 날 Cloudflare(하루 할당량)·Browserbase(월 할당량)가 동시에 소진돼 그룹 자동화가 완전히 멈추는 일이 있었는데, 회장이 **Cloudflare Workers Paid 플랜을 결제**해서 Browser Rendering 무료 한도가 **하루 10분→월 10시간, 동시 3개→10개**로 대폭 늘었다. 재시도해보니 Cloudflare 메인 경로가 바로 복구됐고(Browserbase도 별도로 풀려있었음) 자동화가 정상 재개됨. 이제 이 조합으로 그룹 전체 자동화 수요를 상당 기간 무리 없이 커버할 것으로 보임.
**제기**: GlowHalo 2(하윤), 2026-08-10 — B1(니치 API 프로덕트) RapidAPI Hub 가입 자동화 중 발견
**영향 범위**: 그룹 전체 — Browserbase는 GlowHalo 1(Gumroad/SendOwl/Lemon Squeezy 등)·GlowHalo 2가 공용으로 쓰는 자원. 특정 관계사 소관이 아니라 HQ 결정 사안으로 올림.

## 배경 — 왜 이 검토가 필요한가

이 저장소 실행 환경은 로컬 Chromium(Playwright)으로는 프록시 TLS 지문 차단 때문에 어떤 외부 사이트도 브라우저 자동화가 안 되는 구조적 제약이 있다 (`niche-templates/execution/헤드리스브라우저-프록시-이슈.md` 참고). 2026-08-09에 **Browserbase**(클라우드 원격 브라우저)를 도입해 이 문제를 우회했고, 이후 로그인·가입 자동화(카카오 이모티콘, Gumroad 캡처, SendOwl, Lemon Squeezy, RapidAPI 등)에 그룹 전체가 이걸 공용으로 써왔다.

**문제**: Browserbase 무료 플랜은 **월 1시간**인데, 2026-08-09 하루 만에 GlowHalo 1(SendOwl·Lemon Squeezy 온보딩)과 GlowHalo 2(RapidAPI 가입 시도)가 동시에 많이 써서 **한도가 소진**됐다(`402 Payment Required`). 여러 관계사가 계속 이런 자동화를 늘려갈 걸 감안하면, 지금 구조로는 반복적으로 이 문제를 만날 가능성이 높다.

## 결론 및 제안 — 메인/백업 이원화 (신규 벤더 없이)

새 서비스를 하나 더 늘리는 대신, **이미 계정이 있는 두 곳만으로 이중화**하는 안을 제안한다.

- **메인: Cloudflare Browser Rendering** — 하루 10분 무료, 기존 Cloudflare 계정 재사용(신규 가입 불필요)
- **백업: Browserbase**(현행 유지) — 메인이 하루 소진됐을 때만 사용

두 서비스는 **완전히 별개 계정·별개 할당량**이라 서로 잠식하지 않는다 — 실질적으로 무료 자동화 용량이 늘어나는 효과.

### 전환 용이성 (기술 검증 완료)

두 서비스 모두 결국 Playwright `chromium.connectOverCDP()`에 접속 주소를 넘기는 방식이라, 메인 실패 시 백업으로 자동 전환하는 로직을 코드 몇 줄로 구현 가능:

- Browserbase: `POST /v1/sessions`로 세션 생성 → 받은 `connectUrl`로 접속
- Cloudflare: 세션 생성 API 없이 고정 주소(`wss://api.cloudflare.com/client/v4/accounts/{ACCOUNT_ID}/browser-rendering/devtools/browser?keep_alive=600000`)에 API 토큰을 헤더로 실어 바로 접속

벤더 종속 없이 나중에 셋째 옵션(Bug0 등)으로 갈아 끼우기도 쉬운 구조.

## 확인 필요한 것 (회장 액션 후보)

- 지금 쓰는 `CLOUDFLARE_API_TOKEN`이 Workers 배포용으로 좁게 발급된 토큰이라, **Browser Rendering 권한이 포함돼 있는지 실제로 붙여봐야 확인 가능**. 안 되면 같은 Cloudflare 계정 안에서 권한 하나 추가한 토큰을 새로 발급해야 할 수 있음(신규 가입 아님, 기존 계정 내 토큰 추가 발급 수준의 가벼운 작업 — 발급 자체는 회장 액션 필요, 토큰 값 전달 후 금고 등록·연동은 하윤이 처리).

## 승인되면 진행할 일

1. Cloudflare 토큰 권한 확인/발급
2. 메인(Cloudflare)/백업(Browserbase) 자동 전환 로직 스크립트화, 재사용 가능한 형태로 정리(그룹 공용이므로 특정 관계사 폴더가 아니라 이 문서 옆이나 별도 공용 유틸 위치 검토)
3. RapidAPI 가입 재개(GlowHalo 2 B1) 등 대기 중인 자동화 작업에 실제 적용
4. `niche-templates/execution/헤드리스브라우저-프록시-이슈.md`에 이 결정 반영 링크
