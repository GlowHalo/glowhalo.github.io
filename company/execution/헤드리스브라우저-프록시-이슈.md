# 알려진 이슈 — 이 실행환경에서 헤드리스 Chromium(Playwright)이 프록시를 통한 모든 외부 HTTPS 접속에서 TLS 핸드셰이크 실패 (2026-08-09)

## 증상

`/opt/pw-browsers/chromium`(Playwright 번들 Chromium, 버전 141.0.7390.37)로 프록시(`$HTTPS_PROXY`, `agent proxy`)를 거쳐 **어떤 외부 HTTPS 사이트든** 접속을 시도하면 실패한다.

- 에러: `net::ERR_CONNECTION_RESET` (Playwright 레벨) / 내부 로그: `handshake failed; returned -1, SSL error code 1, net_error -202`(`ERR_CERT_AUTHORITY_INVALID`) 또는 `-101`(`ERR_CONNECTION_RESET`)
- 재현: `example.com` 같은 완전히 무관한 공개 사이트에서도 동일하게 재현됨 — 특정 사이트(Gumroad 대시보드, 카카오 이모티콘 스튜디오 SPA 등)만의 문제가 아니라 **"프록시를 거치는 모든 HTTPS 접속" 자체가 이 환경의 Chromium에서 안 됨**.
- 대조군: 같은 프록시로 `curl -x http://127.0.0.1:37041 --cacert /root/.ccr/ca-bundle.crt https://example.com`는 정상 작동(TLS 1.3, 실제 사이트의 정상 인증서 체인 확인됨 — 프록시가 임의 도메인의 TLS를 실제로 재종단(MITM)하는 것도 아니고 단순 CONNECT 터널링으로 보임). 즉 **프록시 자체는 정상**이고, 문제는 Chromium 141의 인증서 검증 경로에 국한됨.
- Chromium을 프록시 없이 **직접 연결이 허용된 도메인**(`no_proxy` 목록의 `pypi.org` 등)으로 보내면 정상 로드됨 — Chromium 자체의 TLS 스택은 정상, 문제는 "프록시 CONNECT 터널 위에서의 인증서 검증" 경로에서만 발생.

## 시도해본 것 (전부 실패, 순서대로)

1. 기본 실행 (프록시 인자 없음, env의 `HTTPS_PROXY`만 존재) — 실패
2. `--proxy-server=http://127.0.0.1:37041` 명시 — 실패
3. `--no-sandbox --disable-setuid-sandbox` 추가 (컨테이너 환경 표준 플래그) — 실패
4. `--proxy-server=127.0.0.1:37041` (스킴 없는 host:port 표기) — 실패
5. `--ignore-certificate-errors-spki-list=<proxy CA의 SPKI 해시>` (특정 CA만 신뢰 pin, 전면 무시 아님) — 실패, 동일한 `-202` 재현
6. `$HOME/.pki/nssdb`(NSS 인증서 저장소) 확인 — 이미 사전 구성되어 있었음(README의 "browser NSS store already set up"과 일치), 그런데도 실패 — **Chromium 129+는 Linux에서도 OS/NSS 신뢰 저장소 대신 내장 Chrome Root Store를 쓰기 때문에 NSS DB 등록이 더 이상 유효하지 않은 것으로 추정**
7. (진단 목적으로만) `--ignore-certificate-errors` 전체 무시 시도 — **Claude Code 자동승인 분류기가 즉시 차단**함(의도된 안전장치로 판단, 우회 시도하지 않고 중단)

## 결론

이 환경의 Playwright/Chromium으로는 **현재 외부 사이트 로그인·폼제출 등 실제 브라우저 자동화가 불가능**하다(정적 페이지 읽기조차 안 됨). curl/API 기반 호출은 프록시를 통해 정상 작동하므로, **API가 있는 작업은 그대로 진행 가능**하지만, 로그인 세션이 필요한 SPA(카카오 이모티콘 스튜디오, Gumroad 대시보드 브라우저 자동화 등)나 회원가입 폼 자동입력은 이 이슈가 풀리기 전까지 회장이 직접 하거나, 세션이 재구성될 때(새 환경/새 Chromium 빌드) 재시도해야 한다.

## 다음에 이 이슈를 마주치면

1. 위 "시도해본 것"을 반복하지 말 것 — 전부 재현 확인됨.
2. 먼저 `curl -sS "$HTTPS_PROXY/__agentproxy/status"`로 프록시 자체가 살아있는지만 빠르게 확인.
3. 브라우저가 꼭 필요한 작업이면 회장에게 보고하고 수동 진행을 요청하거나, `/root/.ccr/README.md`가 안내하는 대로 Anthropic 지원팀에 리포트하는 걸 회장에게 제안한다(사장이 직접 티켓을 넣을 수단은 없음).
4. API가 있는 채널(Gumroad, Etsy, SendOwl, Lemon Squeezy, Whop, Firefox Add-ons 등)은 이 이슈와 무관하게 정상 진행 가능 — 계정 생성(로그인 폼 제출)만 이 이슈에 걸리고, 발급된 키로 하는 API 호출은 전부 정상.

## 추가 진단 — "Full" 네트워크 정책 세션에서 재검증 (2026-08-09, 같은 날 후속 세션)

위 6번 항목("Chrome Root Store 때문에 NSS DB 등록이 무효"라는 추정)을 별도 세션에서 다시 파봤다. **이 추정은 틀렸다** — 실제로는 그 세션의 `~/.pki/nssdb`가 (README의 "already set up" 서술과 달리) **완전히 비어 있었다.** `apt-get install -y libnss3-tools`로 `certutil`을 설치한 뒤 `certutil -d sql:$HOME/.pki/nssdb -A -t "CT,c,c" -n ccr-agent-proxy -i /root/.ccr/agent-proxy-ca.crt`로 프록시 CA를 직접 임포트하니, 실제 대상 도메인(`example.com`)에 대한 `-202`(`ERR_CERT_AUTHORITY_INVALID`)는 사라졌다 — 즉 NSS DB 등록은 여전히 유효하고, 문제는 그 세션에서 등록 자체가 안 되어 있었던 것뿐이었다.

다만 그 뒤에도 **더 근본적인 2차 차단이 남아있었다**: CA 신뢰 문제를 고친 후에도 여전히 `ERR_CONNECTION_RESET`(`net_error -101`, `os_error 104`=ECONNRESET). `--log-net-log`로 바이트 단위 추적한 결과 — 프록시로의 `CONNECT` 터널 자체(`200 Connection Established`)는 정상 성립하지만, **Chromium이 TLS ClientHello(BoringSSL 특유의 GREASE/ECH-GREASE/포스트퀀텀 키 공유 확장 포함, ~1.7~1.8KB)를 보내는 즉시 서버 쪽이 아무 응답 없이 TCP 연결을 리셋**한다. 같은 세션의 `curl`(더 작고 평범한 ClientHello)은 정상 접속되므로, 이는 인증서 신뢰 문제가 아니라 **TLS ClientHello 크기/확장/핑거프린트(JA3·JA4류) 기준의 차단**으로 강하게 추정된다.

- **"다른 환경/네트워크 정책이면 될 것"이라는 가설도 이번에 기각됨** — 회장이 네트워크 정책을 "Full"(더 넓은 접근)으로 바꾼 별도 세션에서 재시도했지만 동일하게 재현됨. 즉 세션별 네트워크 정책과 무관하게, 모든 세션이 공유하는 아웃바운드 에이전트 프록시(혹은 그 상류 egress gateway) 자체의 구조적 제약이다.
